# Delivery Fleet Allocation Engine

A full-stack web application that solves a real logistics problem: **assigning delivery trucks to orders** across San Francisco. Four algorithms compete — Greedy, Hungarian, a custom Heuristic, and a Machine Learning model — so you can see exactly how each one thinks and where each one wins.

---

## What problem does this solve?

Imagine a dispatch center. Every morning they receive 40–55 delivery orders spread across the city. They have 18–25 trucks, each starting from a different depot, carrying different cargo types (Refrigerated, Heavy Freight, Standard, Express, Fragile), with different shift hours, and a limit on how many deliveries they can make per day. Each order has:

- A **location** somewhere in SF
- A **cargo type** (you can't send a standard truck to transport refrigerated goods)
- A **time window** (the recipient is only available 9am–1pm)
- A **priority** (Critical/Urgent/High/Medium/Low)
- An **estimated unloading duration**

The system must decide: **which truck should handle which delivery order?** This is a version of the classical Assignment Problem, made harder by cargo compatibility constraints, time windows, and the fact that a truck's location and availability changes after each delivery.

## How the code works — a walkthrough

### Data models (`backend/models.py`)

Everything flows through four Pydantic models:

```
Truck
  id, name
  location: { lat, lng, address }     ← starting depot each morning
  cargo_types: [STANDARD, REFRIGERATED, …]  ← which cargo types this truck can carry
  shift_start / shift_end             ← working hours (e.g. 6.0 = 6:00am)
  max_deliveries                      ← capacity cap per shift

DeliveryOrder
  id, description
  location: { lat, lng, address }
  cargo_type                          ← must match a truck's cargo_types (hard constraint)
  priority: 1–5                       ← Low / Medium / High / Urgent / Critical
  window_start / window_end           ← recipient availability window
  duration                            ← estimated unloading time

Assignment
  truck_id, order_id
  distance_km, travel_time_hours
  arrival_time                        ← when the truck arrives
  score                               ← algorithm's internal quality score
  explanation                         ← human-readable reason for this pairing

AllocationResult
  algorithm                           ← which algo produced this
  assignments: [Assignment]
  unassigned_order_ids                ← orders nobody could serve
  metrics: { fulfillment_rate, total_distance_km, load_balance_score, … }
  execution_time_ms
```

### Cargo types (`CargoType` enum)

| Value | Meaning |
|---|---|
| `REFRIGERATED` | Cold chain — vaccines, fresh produce, dairy |
| `HEAVY_FREIGHT` | Machinery, furniture, construction materials |
| `STANDARD` | Parcels, office supplies, general merchandise |
| `EXPRESS` | Same-day urgent — medical, legal, critical parts |
| `FRAGILE` | Art, electronics, scientific instruments |

### Shared math (`backend/algorithms/base.py`)

All algorithms call the same helper functions:

**Haversine distance** — computes the straight-line distance in km between two lat/lng points using spherical geometry. Used instead of road distance (no routing API required).

**Travel time** — `distance_km / 30 km/h` (urban SF speed assumption).

**`can_serve(truck, order, current_time, current_loc)`** — checks hard constraints:
1. Does the truck carry the required cargo type?
2. Can the truck physically reach the order before its window closes?
3. Will the delivery finish before the truck's shift ends?

Returns `(True/False, reason_string)`.

**`assignment_cost(truck, order, …)`** — a scalar score combining:
- Distance (normalized to 0–1 over a 10 km range)
- Priority bonus (higher priority orders are cheaper to serve, assigned first)
- Window urgency (penalty for cutting it close to the deadline)

Lower cost = better assignment. Returns `INFEASIBLE_COST = 1e9` if hard constraints fail.

**`compute_metrics(assignments, …)`** — calculates fulfillment rate, total/average distance, and load balance score (1 − coefficient of variation of deliveries per truck).

## The four algorithms

### Algorithm 1 — Greedy (`greedy.py`)

**The idea:** Process one order at a time, greedily take the best available truck for each.

**Step by step:**
1. Sort all orders: highest priority first, then tightest deadline.
2. For each order, loop over every truck:
   - Skip if at max capacity or wrong cargo type.
   - Compute `assignment_cost()` from the truck's **current location** (not depot — this is key).
   - Track which truck has the lowest cost.
3. Assign that truck. Update its state: new location = order location, new time = delivery end time.
4. Move to the next order.

**Why "current location" matters:** After a truck completes delivery A, its next cost is calculated from delivery A's location, not the depot. This naturally chains deliveries that are geographically close — implicit route optimization.

**The tradeoff:** Committing to each assignment before seeing the rest means a greedy choice early can block a better global solution later.

---

### Algorithm 2 — Hungarian (`hungarian.py`)

**The idea:** Look at all possible truck–order pairings at once and find the globally cheapest assignment.

**Step by step:**
1. Expand each truck into N "slots" (one per `max_deliveries`). A truck with capacity 8 becomes 8 virtual rows.
2. Build a cost matrix: rows = truck-slots, columns = orders. Each cell = `assignment_cost()` from the truck's depot. Infeasible pairs get cost = 1e9.
3. Run `scipy.optimize.linear_sum_assignment(cost_matrix)` — the Kuhn-Munkres algorithm, O(n³). Finds the assignment that minimizes total cost.
4. Filter out pairings with infeasible cost.

**The key difference from Greedy:** Sees the entire board before making any decision. Can sacrifice a locally-cheap assignment to free up a truck for a globally better use.

**The limitation:** All slots use the depot location — the algorithm can't know in advance what order a truck's multiple deliveries will be visited, so it can't chain routes. This is why Hungarian doesn't always dominate on distance despite being "optimal."

---

### Algorithm 3 — Priority-Cluster Heuristic (`heuristic.py`)

**The idea:** Group geographically nearby orders into clusters, then route trucks through their assigned cluster. Reduces cross-city travel while still respecting priority.

**Step by step:**
1. Run k-means clustering on order locations (k = number of trucks ÷ 2). Pure Python — implements centroid iteration without sklearn.
2. Sort clusters by total priority weight (most critical cluster first).
3. For each cluster, rank trucks by: cargo overlap + proximity to cluster centroid + current load.
4. Within each cluster, serve orders in priority order using route chaining (updates truck location after each delivery).
5. Second pass: any orders that didn't fit a cluster get assigned via greedy fallback.

**Load balance soft constraint:** Each truck gets a `load_factor = current_deliveries / max_deliveries` added to its cost. This discourages piling all deliveries onto one truck.

### Algorithm 4 — ML (`ml_allocator.py`)

Instead of a hand-crafted cost formula, this uses a **RandomForest model trained on synthetic historical dispatch data** to predict the quality of any truck–order pairing.

#### Is there real training data?

No — in a real system you'd feed in months of historical dispatches labeled with outcomes. We don't have that, so we **generate synthetic history**.

#### How synthetic history is generated

`_generate_training_data()` runs the following loop 1,650 times:

```
Create a random scenario:
  - 5–14 trucks at random SF locations with random cargo types and shift hours
  - 8–24 delivery orders at random SF locations with random cargo, priorities, windows

For each (truck, order) pair in this scenario:
  - Extract 9 features describing this pairing
  - Compute a quality label (0.0 to 1.0)
  - Store as one training example
```

Plus the real seed data (12 trucks, 20 orders) is always included as one scenario.

Total: ~250,000 labeled training examples across 1,651 scenarios.

#### The 9 features

| Feature | What it captures |
|---|---|
| `distance_km` | How far the truck has to travel |
| `travel_time_h` | Estimated drive time |
| `cargo_match` | 1.0 if truck can carry the cargo type, 0.0 if not |
| `window_slack_h` | Hours of buffer before the window closes after arrival |
| `wait_time_h` | How long the truck waits if it arrives before the window opens |
| `priority` | Order urgency (1–5) |
| `duration_h` | How long unloading takes |
| `truck_hours_remaining` | How much shift the truck has left |
| `load_ratio` | Truck's current deliveries / max deliveries (workload) |

#### The quality label

Each training example is labeled with a score from 0 to 1:

```python
def quality_label(truck, order, arrival, dist, load_ratio):
    if cargo mismatch:              return 0.0   # hard fail
    if arrival > window_end:        return 0.0   # hard fail
    if delivery exceeds shift end:  return 0.0   # hard fail

    dist_score     = 1.0 - (dist / 20km)         # shorter = better
    time_score     = slack / window_size          # more buffer = better
    load_score     = 1.0 - load_ratio             # less loaded = better
    priority_score = priority / 5                 # higher priority = better

    return 0.35 * dist_score
         + 0.20 * time_score
         + 0.20 * load_score
         + 0.25 * priority_score
```

The weights represent domain knowledge embedded in label generation, not hard-coded into the algorithm itself.

#### What the model learned

After training on ~250,000 examples, the RandomForest's feature importances reveal:

| Feature | Importance |
|---|---|
| Cargo match | ~62% |
| Time-window slack | ~29% |
| Truck hours remaining | ~5% |
| Priority | ~2% |
| Distance | ~1% |

**The key insight the ML surfaces:** Distance barely matters. Getting the right cargo type into an open time window is what separates good assignments from bad ones. The hand-tuned algorithms put distance at 35% weight — the model says that's wrong by a factor of 35x.

This is why ML's total distance is typically higher than the others: it deliberately accepts longer drives when they secure a better cargo+window match.

#### Inference

At dispatch time, for each order (processed in priority order):
1. Check all trucks against hard constraints.
2. For the feasible ones, compute the 9-feature vector.
3. Batch-predict quality scores using the trained model.
4. Assign the highest-scoring truck.
5. Update truck state (route-chaining, like Greedy).

The explanation field on each assignment shows the top 3 features that drove the decision.

#### Model persistence

The trained model is saved to `backend/data/ml_model.pkl`. On subsequent server starts it loads from disk instantly. The `/api/ml/train` endpoint retrains in the background if called.

## Algorithm comparison summary

| | Greedy | Hungarian | Heuristic | ML |
|---|---|---|---|---|
| Total distance | ~low | **lowest** ✓ | ~low | ~higher |
| Load balance | ~54% | ~61% | **~68%** ✓ | ~63% |
| Fulfillment | 100% | 100% | 100% | 100% |
| Speed | **< 1 ms** ✓ | ~1 ms | ~1 ms | ~50 ms |
| Route chaining | Yes | No | Yes | Yes |

> Note: exact distance and balance numbers vary each run because the scenario is randomized on every backend startup.

**Use Greedy** when: orders arrive throughout the day (real-time dispatch). Route chaining handles a moving truck better than any batch algorithm.

**Use Hungarian** when: scheduling tomorrow's deliveries tonight. Full batch visibility gives the globally optimal distance.

**Use Heuristic** when: driver fairness matters (overtime costs, labor rules). Its load-balance constraint distributes deliveries most evenly.

**Use ML** when: you want the system to discover what matters — not what you think matters. The model reveals that distance is nearly irrelevant compared to cargo matching and time-window utilization, which challenges the assumption baked into the other three algorithms.

See `ANALYSIS.md` for a deeper discussion.
